# ADR-009: รวม "ความคืบหน้าการวิวัฒน์อาวุธ" ไว้ที่เดียว

**Status:** Accepted — **เจ้าของเลือกทางที่แรงกว่าที่เสนอ: ถอดระบบแนะนำทิ้งทั้งระบบ**
ลงมือแล้วฝั่งโค้ด (Roslyn สะอาดทั้งสอง assembly) · เหลือ prefab กับการตรวจสามชั้น
**Date:** 2026-09-14
**Deciders:** เจ้าของโปรเจกต์
**ที่มา:** คำถาม "Evolution Synergy กับระบบแนะนำต่างกันยังไง" แล้วไล่อ่าน `UpgradeManager` ทั้งไฟล์

---

## Decision ที่เจ้าของตัดสิน — แทนที่ข้อเสนอเดิมทั้งหมด

> *"อยากให้ระบบ recommend ออก เพราะเป็นการชักจูงผู้เล่นมากเกินไป อยากให้ผู้เล่นเลือกเอง
> แต่เก็บแค่ Evolution Synergy ก็เพียงพอแล้ว"*

เอกสารนี้เดิมเสนอให้ **รวม** ตรรกะของสามระบบเข้าด้วยกัน · เจ้าของตัดสินให้ **ลบหนึ่งในสามทิ้ง**
ซึ่งแก้ปัญหาเดียวกันได้ดีกว่าและถูกกว่า — ปัญหาคือ "สามที่เห็นโลกไม่ตรงกัน"
เหลือสองที่ก็ตัดความไม่ตรงกันไปหนึ่งคู่ทันที โดยไม่ต้องสร้างนามธรรมใหม่มาคุม

**เหตุผลของการตัดสินเป็นเรื่องดีไซน์ ไม่ใช่เรื่องโครงสร้างโค้ด** — เกมโรกไลก์ที่ดีอยู่ที่
การตัดสินใจของผู้เล่น ป้าย "แนะนำ" ทำให้การตัดสินใจนั้นเหลือแค่การอ่านป้าย
เอกสารนี้เถียงเรื่องความสอดคล้องของโค้ดอยู่ดีๆ แล้วคำตอบที่ถูกคือคำถามว่า
**ระบบนี้ควรมีอยู่ไหมตั้งแต่แรก** ซึ่งโค้ดตอบเองไม่ได้

### เส้นแบ่งที่ต้องรักษาจากนี้ไป

| บอกได้ | บอกไม่ได้ |
|---|---|
| "Laser Lv5 · ขาด Armor อีก 2" | "ควรเอา Armor" |
| "Armor Lv1/3" | "ใบนี้คุ้มที่สุด" |
| อะไรเชื่อมกับอะไร · ห่างอีกเท่าไร | ใบไหนดีกว่าใบไหน |

เขียนไว้เป็นคอมเมนต์หัวบล็อกใน `UpgradeManager.PopulateSynergyInfo` ด้วย
เพราะเป็นกติกาที่คนมาทีหลังต้องเห็นตอนแก้ ไม่ใช่ตอนไปขุดเอกสาร

### สิ่งที่ Evolution Synergy ต้องแบกแทน

พอเป็น **ช่องทางเดียว** แล้ว ไอคอนเปล่าๆ ไม่พออีกต่อไป — เดิมมันเป็นของประกอบ
ตอนนี้มันคือทั้งหมดที่เกมบอก · จึงยกเครื่องจาก `List<Sprite>` เป็น `List<SynergyLine>`
ที่มีชื่อ สภาพปัจจุบัน และธงว่าเงื่อนไขครบหรือยัง

### สิ่งที่ **ไม่** ทำตามข้อเสนอเดิม

`EvolutionProgress` ที่เสนอไว้ **ไม่ถูกสร้าง** — มันมีเหตุผลตอนที่มีผู้อ่านสามคน
เหลือผู้อ่านสองคน (`CheckSuperConditions` กับ `PopulateSynergyInfo`) และคนหนึ่ง
ต้องการ `bool` อีกคนต้องการข้อความ การสร้างชั้นกลางมาคุมสองคนนี้คือนามธรรม
ที่แพงกว่าปัญหา · ถ้าวันหนึ่งมีผู้อ่านคนที่สามค่อยกลับมาอ่านข้อเสนอเดิม

## Context

คำถามตั้งต้นคือ *"ระบบแนะนำไม่ได้ไปอ่านระบบ evo weapon เลย"*

**ไม่ตรงเสียทีเดียว — มันอ่าน แต่อ่านไม่ครบและอ่านคนละแบบกับอีกสองที่**
`RecommendCards` อ่าน `superConditions` จริงในสาขาการ์ดสเตตัส (`UpgradeManager.cs:196-211`)
แต่อ่านเฉพาะ `StatAtLevel` และตัดสินแบบ binary เท่านั้น

ปัญหาที่แท้จริงใหญ่กว่าคำถามเดิม: คำว่า **"อาวุธนี้ใกล้วิวัฒน์แค่ไหน"**
ถูกตอบอยู่ **สามที่ ด้วยตรรกะคนละชุด** และไม่มีที่ไหนอ้างอิงกันเลย

| ที่ | หน้าที่ | อ่านอะไร | ไม่อ่านอะไร |
|---|---|---|---|
| `CheckSuperConditions` (`:736`) | **ประตูจริง** ตัดสินว่าได้/ไม่ได้ | ครบทั้ง 3 ชนิดเงื่อนไข เทียบเลเวลจริง | เลเวลอาวุธ (คนเรียกเช็คแยก) |
| `PopulateSynergyInfo` (`:283`) | **ป้ายบอกทาง** ไอคอนก้นการ์ด | `StatAtLevel` · `GetStatLevel > 0` · `HasProgressedPast` | `WeaponAtLevel` · `PlayerLevel` · เลเวลอาวุธ |
| `RecommendCards` (`:112`) | **คำแนะนำ** ป้าย "แนะนำ" | `StatAtLevel` แบบ binary | `WeaponAtLevel` · `PlayerLevel` · เลเวลอาวุธ · ระยะห่างที่เหลือ |

สามชุดนี้ **เห็นโลกไม่ตรงกัน** ทั้งที่ตอบคำถามเดียวกัน

---

## อาการที่เกิดขึ้นจริงวันนี้

### 🔴 คำแนะนำไม่รู้ว่าอาวุธอยู่เลเวลไหน

`RecommendCards` ให้สเตตัสที่ปลดล็อก Super `+12` เท่ากันหมด โดย**ไม่ดูเลยว่าอาวุธนั้นถึง Lv5 หรือยัง**

```csharp
// UpgradeManager.cs:196-211 — ไม่มีการเช็ค GetWeaponLevel(w) ที่ไหนเลย
if (cond.conditionType == SuperConditionType.StatAtLevel &&
    cond.requiredStatType == card.stat.statType)
{
    int currentLv = statManager.GetStatLevel(cond.requiredStatType);
    if (currentLv < cond.requiredLevel) score += 12f;
}
```

ผลคือ:

| สถานการณ์ | ควรแนะนำแค่ไหน | ได้จริง |
|---|---|---|
| Laser **Lv5** ขาด Armor อีก 1 เลเวลก็ขึ้น Super | สูงที่สุด | +12 |
| Laser **Lv1** ขาด Armor อีก 4 เลเวล | แทบไม่ควรแนะนำ | +12 |

ใบที่พาไปถึงเป้าทันทีกับใบที่ยังอีกไกล **ได้คะแนนเท่ากันเป๊ะ**

### 🔴 "ใกล้ขึ้น Super" ที่ไม่ได้เช็คว่าใกล้จริงไหม

```csharp
// UpgradeManager.cs:137-140
if (card.weapon.tier == WeaponTier.Normal && card.targetLevel == card.weapon.MaxLevel)
    score += 5f; // ใกล้ขึ้น Super
```

`+5` นี้ดูแค่ว่าการอัปครั้งนี้พาไป Lv5 ไหม — **ไม่ดูเงื่อนไขสเตตัสเลย**
อาวุธที่ขาดสเตตัสอีกสี่เลเวลก็ยังได้ `+5` พร้อมคอมเมนต์ว่า "ใกล้ขึ้น Super"

### 🟡 คะแนน 20 ของ Super/Fusion แทบไม่ได้ทำงาน

`score = 20f` ให้กับการ์ด Super/Fusion — แต่การ์ดสองชนิดนี้**ออกมาจาก `BuildOrbPool` ทางเดียว**
(`BuildLevelUpPool` ไม่มีทั้งคู่) และ orb แจกใบเดียว จึงแทบไม่มีอะไรให้เทียบคะแนนด้วย
เลขนี้เป็นน้ำหนักที่ดูสำคัญแต่ไม่ค่อยมีผล

### 🟡 ไอคอน synergy ใบที่สามหายเงียบ

`UpgradeManager` ตัดไว้ที่ 3 (`:365`) แต่การ์ด P3R สร้างช่องไว้ 2
(`P3RLevelUpSceneBuilder.cs:594` — `for (int s = 0; s < 2; s++)`)
และ `UpgradeCardUI:144` วนตาม `synergyIconImages.Count` ไม่ใช่ตามจำนวนรูปที่ได้รับ
→ รูปที่สามถูกทิ้งโดยไม่มีอะไรฟ้อง

เกิดได้ทางการ์ดสเตตัส: ถือ Normal สามตัวที่วิวัฒน์ด้วยสเตตัสเดียวกัน

### ⚪ ยังไม่เกิด แต่รออยู่ (latent)

ตรวจ asset จริงแล้ว — ทั้งสองข้อนี้**ยังไม่เป็นปัญหาวันนี้** แต่จะระเบิดทันทีที่คอนเทนต์เปลี่ยน

| ข้อ | สภาพคอนเทนต์ตอนนี้ | จะพังเมื่อ |
|---|---|---|
| `WeaponAtLevel` / `PlayerLevel` ไม่ถูกอ่านโดยทั้ง synergy และ recommend | `WeaponData` 0 ไฟล์ที่ใช้สองชนิดนี้ (ใช้ `StatAtLevel` 23 ไฟล์) | ดีไซเนอร์ใส่เงื่อนไขชนิดใหม่ใบแรก |
| `+5` ไม่เช็ค `superVersion != null` | Normal ทั้ง 20 ตัวมี `superVersion` ครบ | เพิ่มอาวุธ Normal ที่ไม่มี Super |

**นี่คือเหตุผลที่ควรรวมตอนนี้** — ตอนที่ยังเป็นแค่ความไม่สอดคล้อง ไม่ใช่ตอนที่เป็นบั๊ก

## Decision

เพิ่ม **`EvolutionProgress`** เป็น query ตัวเดียวที่ตอบว่า "อาวุธนี้ห่างจากการวิวัฒน์แค่ไหน"
แล้วให้ทั้งสามที่อ่านจากมัน

```
       WeaponData.superConditions ─┐
       PlayerStatManager ──────────┤
       PlayerWeaponManager ────────┤
       SharedExperienceManager ────┘
                    │
                    ▼
          ┌──────────────────┐
          │ EvolutionProgress │  query ล้วน ไม่รู้จัก UI ไม่รู้จัก UpgradeCardType
          └──────────────────┘
              │      │      │
    ┌─────────┘      │      └──────────┐
    ▼                ▼                 ▼
CheckSuperConditions  PopulateSynergy   RecommendCards
  "ผ่านไหม"           "โชว์ไอคอนอะไร"    "ให้กี่คะแนน"
```

### รูปร่างข้อมูล

```csharp
/// ระยะห่างจากการวิวัฒน์หนึ่งก้าว — Normal → Super
public readonly struct EvolutionStep
{
    public readonly WeaponData      normal;
    public readonly WeaponData      super;
    /// ยังต้องอัปอาวุธอีกกี่เลเวลถึงจะถึง Lv5 · 0 = ถึงแล้ว
    public readonly int             weaponLevelsShort;
    /// เงื่อนไขที่ยังไม่ผ่าน พร้อมว่าขาดอีกเท่าไร
    public readonly UnmetCondition[] unmet;

    public bool Ready => weaponLevelsShort == 0 && unmet.Length == 0;
    /// จำนวน "การ์ดที่ต้องกด" ที่เหลือโดยประมาณ — ใช้ให้คะแนนตามระยะ
    public int StepsRemaining => weaponLevelsShort + unmet.Sum(u => u.levelsShort);
}
```

### จุดสำคัญของการออกแบบ

**`StepsRemaining` เป็นตัวเลข ไม่ใช่ bool** — นี่คือหัวใจ
ทั้งสามที่ต้องการ "ระยะ" คนละความละเอียด: ประตูอยากได้ `== 0` ป้ายอยากได้ `> 0` ไหม
คำแนะนำอยากได้ตัวเลขจริงเพื่อให้คะแนนตามระยะ · ตัวเลขตอบได้ทั้งสาม bool ตอบได้แค่ข้อเดียว

**ไม่รู้จัก `UpgradeCardType` และไม่รู้จัก UI** — ไม่งั้นมันจะกลายเป็น `UpgradeManager` ก้อนที่สอง
รับแค่ผู้เล่นกับข้อมูล คืนข้อเท็จจริง ใครจะเอาไปทำป้ายหรือคะแนนเป็นเรื่องของคนเรียก

**รวมเฉพาะ Super ก่อน ไม่รวม Fusion** — Fusion ไม่มีเงื่อนไขให้คืบหน้า
มันเป็น "มีครบสองชิ้นไหม" ซึ่งเป็น bool จริงๆ ยัดเข้าโครงเดียวกันจะได้ field ที่ว่างครึ่งนึงตลอด

### การ์ดสเตตัสให้คะแนนตามระยะ

```csharp
// แทน +12 คงที่
foreach (var step in EvolutionProgress.BlockedBy(card.stat.statType, pwm, psm))
{
    if (step.weaponLevelsShort > 0) score += 4f;   // อาวุธยังไม่ถึง Lv5 — ยังไม่ใช่คอขวด
    else if (step.StepsRemaining == 1) score += 18f; // ใบนี้จบ ปลดล็อกทันที
    else score += 12f - step.StepsRemaining;        // ยิ่งใกล้ยิ่งสูง
}
```

ตัวเลขข้างบนเป็น **ตุ๊กตาให้เห็นรูปร่าง ไม่ใช่ข้อเสนอบาลานซ์** — ดูข้อ 1 ท้ายเอกสาร

## ทางเลือกที่พิจารณาแล้วไม่เอา

| ทางเลือก | ข้อดี | ทำไมไม่เอา |
|---|---|---|
| **ปะเฉพาะจุด** — เติมเช็คเลเวลอาวุธใน `RecommendCards` ~15 บรรทัด | ถูกที่สุด เสี่ยงน้อยสุด ไม่แตะไฟล์อื่น | ยังเหลือตรรกะสามชุด · ครั้งหน้าที่เพิ่มชนิดเงื่อนไขก็ต้องแก้สามที่อีก |
| **ให้ `RecommendCards` เรียก `CheckSuperConditions` ตรงๆ** | ไม่ต้องมีไฟล์ใหม่ | มันคืน `bool` — ได้แค่ "ผ่าน/ไม่ผ่าน" ซึ่งไร้ประโยชน์กับการให้คะแนน เพราะคนที่ยังไม่ผ่านคือทุกคน |
| **ย้าย synergy ไปเป็นผลพลอยได้ของ recommend** | เหลือระบบเดียวจริงๆ | สองอย่างนี้**ตอบคนละคำถาม** — "ควรกดใบไหน" กับ "ใบนี้เกี่ยวกับอะไรที่ฉันมี" · ยุบรวมแล้วจะเสียป้ายบอกทางบนใบที่ไม่ได้ถูกแนะนำ ซึ่งเป็นใบที่ต้องการคำอธิบายที่สุด |
| **ไม่ทำอะไร** | ฟรี | ความไม่สอดคล้องจะกลายเป็นบั๊กทันทีที่ดีไซเนอร์ใช้ `WeaponAtLevel` ใบแรก |

## Consequences

### ได้

- สามที่เห็นโลกตรงกันโดยโครงสร้าง ไม่ใช่โดยวินัยของคนแก้
- เพิ่มชนิดเงื่อนไขใหม่ = แก้ที่เดียว จากเดิมสามที่ (และเดิมลืมสองที่ทุกครั้ง)
- คำแนะนำแยกออกได้ว่า "ใบนี้จบเลย" กับ "ใบนี้ยังอีกไกล" ซึ่งตอนนี้แยกไม่ได้
- เขียนเทสต์ได้จริง — `EvolutionProgress` เป็น query ล้วน ไม่ต้องมีซีนหรือ play mode

### เสีย

- ไฟล์ใหม่ ~120 บรรทัด + แก้ call site สามจุด
- **คะแนนแนะนำจะเปลี่ยน** = สิ่งที่เกมชี้ให้ผู้เล่นกดเปลี่ยน · นี่คือ**การเปลี่ยนบาลานซ์ ไม่ใช่ refactor เฉยๆ** ต้องเล่นจริงดู
- `RecommendCards` จะยาวขึ้นช่วงแรกระหว่างที่ยังเก็บของเดิมไว้เทียบ

### ที่ต้องกลับมาดูเมื่อระบบโต

- ถ้ามี Fusion ที่มีเงื่อนไข (ไม่ใช่แค่ "มีครบสองชิ้น") ต้องรื้อ `EvolutionStep` ให้รับหลายก้าว
- ถ้า augment เข้ามาเกี่ยวกับการวิวัฒน์ ต้องเพิ่ม `PlayerAugmentManager` เป็น input
- ถ้าจำนวนไอคอน synergy ยังไม่ตรงกันระหว่างข้อมูลกับการ์ด ปัญหานี้จะโผล่ซ้ำในรูปแบบอื่น

---

## ต้องให้เจ้าของตัดสิน — ไม่ใช่เรื่องที่โค้ดตอบได้

**1. คะแนนใหม่ควรเป็นเท่าไร**
การให้คะแนนตามระยะเปลี่ยนว่าเกมชี้ให้กดอะไร — เป็นเรื่องดีไซน์ ไม่ใช่เรื่องถูก/ผิด
ทางที่ปลอดภัยคือเฟสแรก map ให้ได้ผลเท่าเดิมเป๊ะ (ทุกอย่าง `+12` เหมือนเดิม)
แล้วค่อยเปิดการให้คะแนนตามระยะเป็นก้าวที่สอง — จะได้รู้ว่าอะไรทำให้ความรู้สึกเปลี่ยน

**2. ไอคอน synergy เอากี่ช่อง**
